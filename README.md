# USERS-microservice (users-service)

![Java Version](https://shields.io)
![Spring Boot](https://shields.io)
![Spring Security](https://shields.io)
![gRPC](https://shields.io)


Микросервис управления пользователями, аутентификации и авторизации. Данный компонент выступает единым центром безопасности системы: он хранит учетные данные, регистрирует аккаунты, генерирует JWT-токены, а также предоставляет внутренний высокоскоростной gRPC-интерфейс для игрового движка.

## 🛠️ Стек технологий и особенности

* **Язык и ядро:** Java 21 со включенными виртуальными потоками (Virtual Threads). Благодаря кастомному `GrpcServerConfigurer`, обработка входящих gRPC-запросов полностью переведена на легковесные потоки Loom, минуя ограничения пула ОС-потоков.
* **Фреймворк:** Spring Boot 3.4.2 + Spring Cloud 2024.0.0 (Netflix Eureka Client).
* **База данных:** PostgreSQL + Spring Data JPA + Управление транзакциями (`@Transactional`).
* **Решение проблемы N+1 (Оптимизация JPA):** Запросы чтения `GetAllUsers` и `FindByUsername` переведены на кастомные методы репозитория с JPQL-оператором `LEFT JOIN FETCH`. Это позволило ликвидировать каскад скрытых деструктивных N+1 запросов к таблице ролей и схлопнуть их в один атомарный SQL `JOIN` на стороне СУБД.
* **Упреждающий прогрев планов (JPA Warmup):** Реализован утилитарный конфигурационный класс `HibernateWarmupConfig` для упреждающего прогрева скомпилированных планов сложных кастомных SQL-запросов при старте инстанса в тяжелом ОС-потоке `[main]`. Это полностью устранило проблему Thread Pinning (`reason: MONITOR` в `ConcurrentHashMap`) в рантайме виртуальных потоков.
* **Кэширование:** Локальный высокопроизводительный In-Memory кэш Caffeine (`sync = true`). Используется как первый контур обороны для мгновенной отдачи gRPC Protobuf DTO-сообщений из оперативной памяти, защищая СУБД от лавинных нагрузок и экономя такты CPU на операциях маппинга объектов.
* **Оптимизация под Loom:** Пул соединений HikariCP расширен до **50** соединений. Это обеспечивает оптимальный баланс и предотвращает нехватку коннектов к СУБД при лавинообразном росте параллельных виртуальных потоков.
* **Безопасность:** Spring Security + BCryptPasswordEncoder для хэширования паролей. Генерация JWT-токенов (алгоритм HS256) с зашитым внутрь `userId`. Процесс аутентификации изолирован внутри виртуальных потоков, что позволяет масштабировать сессии пользователей без задержек.

## 🔀 Сетевые интерфейсы и Порты

Микросервис работает одновременно в двух сетевых режимах:

* **HTTP Порт (4444):** Используется для работы с веб-страницами (Thymeleaf) и REST API.
* **gRPC Порт (6567):** Выделенный порт для внутреннего взаимодействия. Порт автоматически передается в метаданных на сервер Eureka, что позволяет игровому движку находить gRPC-сервер динамически.

## 🔌 API Endpoints (HTTP REST & UI)

Доступ к этим эндпоинтам открыт напрямую на уровне внутренней безопасности, финальную фильтрацию трафика выполняет шлюз API Gateway.

### Интерфейс (UI Thymeleaf)
* `GET /login` — Страница авторизации пользователя.
* `GET /registration` — Страница регистрации нового аккаунта.

### REST API
* `POST /api/users/register` — Регистрация нового аккаунта. Принимает имя, пароль, подтверждение пароля. Новым пользователям автоматически присваивается базовая роль (`ROLE_USER`).
* `POST /api/users/login` — Авторизация. Проверяет пароль через BCrypt, генерирует и возвращает JWT-токен (время жизни — 24 часа) и `userId`.

## 🛰️ Контракт gRPC Сервиса (UserService)

Внутренний интерфейс взаимодействия, описанный в Protobuf, предоставляет игровому движку и другим сервисам следующие RPC-методы:

1. **Поиск и чтение данных:**
    * `FindByUsername` — Поиск информации о пользователе по его логину.
    * `FindById` — Поиск пользователя по его уникальному ID.
    * `GetAllUsers` — Быстрая выгрузка списка всех зарегистрированных пользователей системы.

2. **Модификация данных:**
    * `SaveUser` — Сохранение или обновление данных пользователя (с конвертацией Protobuf в JPA модели).
    * `DeleteUser` — Удаление пользователя по ID с каскадным сбросом связанных ролей.

3. **Инициализация и обслуживание БД:**
    * `IsRolesEmpty` — Проверка наличия ролей в базе данных.
    * `PrepareRolesDB` — Первичный запуск системы: создание системных ролей (`ROLE_ADMIN` с ID 1, `ROLE_USER` с ID 2).
    * `PrepareUserDB` — Создание дефолтного администратора (`admin` / `sam`) с привязкой соответствующей роли.

## ⚡ Логика работы кэша, Ликвидация N+1 и Эволюция прогрева ORM

Для жесткой оптимизации нагрузки на PostgreSQL настроено два кэш-контура с временем жизни записей в 10 минут (максимум 500 элементов) с помощью библиотеки Caffeine:
* **`users_list`** — Кэширует общий список пользователей в gRPC-формате Protobuf DTO и в виде JPA-сущностей для веб-интерфейса.
* **`user_details`** — Кэширует точечные запросы по ID или Username для всех слоев приложения.

### 🛡️ Хронология инженерной защиты от отказов и оптимизации:

1. **Ликвидация деструктивной проблемы N+1 (SQL-уровень):**
   Изначально стандартные методы Spring Data JPA выгружали сущность `User` отдельно, а её ленивую коллекцию ролей (`@ManyToMany(fetch = FetchType.LAZY)`) дозапрашивали каскадом в цикле маппинга. Это приводило к катастрофическому паттерну N+1 (например, 101 SQL-запрос для извлечения 100 пользователей).
   Для решения проблемы были спроектированы кастомные JPQL-запросы с оператором **`LEFT JOIN FETCH`**:
   * `findAllWithRoles()` — стягивает всех пользователей и их роли за один атомарный SQL-шаг.
   * `findByUsernameWithRoles()` — оптимизирует поиск и верификацию пользователя при авторизации до одного обращения к СУБД.

2. **Столкновение с Thread Pinning в Project Loom (Рантайм-уровень):**
   После внедрения кастомных `JOIN FETCH` запросов, в процессе трассировки виртуальных потоков (`-Djdk.tracePinnedThreads=short`), была обнаружена скрытая архитектурная уязвимость. При самом первом («холодном») вызове этих кастомных методов, Hibernate запускал тяжелый процесс компиляции текстовой строки JPQL в нативный SQL-шаблон и инструкцию сборки объектов (`ConcreteSqmSelectQueryPlan.withCacheableSqmInterpretation`).
   Внутри этого процесса Hibernate обращался к стандартному методу Java `ConcurrentHashMap.compute()`. В JDK 21 данный метод содержит блок `synchronized`, из-за чего виртуальный поток совершал **Thread Pinning** — намертво привязывался (блокировал) физический поток ОС (Carrier Thread), снижая общую пропускную способность Loom.

3. **Решение проблемы: Упреждающий прогрев ORM (JPA Warmup) при старте:**
   Чтобы полностью исключить этот пиннинг в рантайме, был разработан конфигурационный класс `HibernateWarmupConfig`, реализующий интерфейс `ApplicationListener<ApplicationReadyEvent>`.
   * **Суть идеи:** Мы перенесли всю тяжелую работу по парсингу, компиляции и кэшированию планов запросов на этап подготовки инстанса микросервиса.
   * **Механика выполнения:** Прогрев принудительно вызывает методы **самого сервисного слоя `UsersService`** (включая сквозной прогрев кэша Caffeine и холостую инициализацию коллекций ролей через `.size()`) **строго на этапе старта приложения внутри классического тяжелого потока ОС `[main]`**. Так как платформенные потоки не подвержены эффекту Thread Pinning, блокировки `synchronized` внутри `ConcurrentHashMap` отрабатывают бесшумно для рантайма еще до открытия портов gRPC/HTTP и начала приема трафика.
   * **Профит в продакшене:** Сгенерированные планы запросов становятся **абсолютно универсальными, неизменяемыми и потокобезопасными трафаретами**. Когда в рантайме тысячи параллельных виртуальных потоков (`Virtual Threads`) начинают одновременно «петрушить» инстанс, они полностью минуют логику компиляции и синхронизированные мапы. Они параллельно, без единого замка берут этот готовый трафарет, подставляют ID и мгновенно улетают в базу данных, демонстрируя чистую I/O-производительность.

4. **Тотальная защита от лавинных запросов (Thundering Herd Protection):**
   Все методы чтения защищены параметром `sync = true` в аннотациях `@Cacheable`. В случае сброса кэша при лавинообразном наплыве параллельных вызовов от Тетриса, Caffeine заблокирует дублирующие потоки. В базу данных пойдет ровно один поток для наполнения кэша, а остальные дождутся ответа из памяти, полностью исключая CPU-Spikes на стороне PostgreSQL.
   *(Для полной безопасности инвалидация кэша в методах изменений настроена с флагом `beforeInvocation = true`, исключая грязное чтение до коммита транзакции).*

5. **План перехода на распределенный кэш (Production Readiness):**
   Текущий локальный In-Memory кэш Caffeine идеально оптимизирован для работы в рамках одного инстанса. При горизонтальном масштабировании сервиса в Kubernetes (запуск 2+ экземпляров за шлюзом API Gateway), для предотвращения рассинхронизации локальных кэшей (`Cache Eviction Race`), архитектура предусматривает бесшовную замену провайдера Caffeine на **распределенный глобальный кэш Redis** через подключение `spring-boot-starter-data-redis` без изменения кода бизнес-логики.

   * **⚠️ ВАЖНОЕ АРХИТЕКТУРНОЕ ПРИМЕЧАНИЕ (Исчерпывающая матрица Thread Pinning в Java 21):**
     Благодаря упреждающему прогреву на слое сервиса (`HibernateWarmupConfig`), все тяжелые системные компиляции JPQL-планов Hibernate и стартовые ячейки известных ключей (например, `'allUsers'`, `'all_proto'`, `"admin"`) успешно создаются тяжелым ОС-потоком `[main]` до открытия портов приложения.

   Тем не менее, при работе под флагом трассировки `-Djdk.tracePinnedThreads=short` в консоли может фиксироваться кратковременное предупреждение `VirtualThread reason: MONITOR` на строке `java.base/java.util.concurrent.ConcurrentHashMap.compute`.

   Инженеринг рантайма определяет ровно **5 сценариев**, при которых ленивая инициализация структур Java 21 провоцирует данный эффект:

   1. **Регистрация нового пользователя (`POST /api/users/register`):** При вводе неизвестного ранее имени (`user99`) метод проверки `findByUsername` принудительно вызывает `ConcurrentHashMap.computeIfAbsent()`. Так как текстового ключа в RAM не существовало, выделение бакета памяти блокируется через `synchronized(node)`. Параллельно шифратор `BCrypt.encode()` обращается к `SecureRandom` для генерации энтропии, где внутри JDK также зашиты мониторы синхронизации пула байт.
   2. **Удаление любого пользователя администратором (`gRPC deleteUser`):** Срабатывание триггеров тотальной очистки контуров списков и деталей (`@CacheEvict(allEntries = true, beforeInvocation = true)`). Операция полной зачистки хэш-мапы (`ConcurrentHashMap.clear()`) блокирует сегменты памяти через внутренние мониторы Java.
   3. **Первый вызов существующего пользователя по динамическому ID (`gRPC findById`):** На этапе старта невозможно предугадать автоинкрементные ID, которые PostgreSQL выдаст реальным игрокам (например, `ID 343`). При первом запросе профиля Spring Cache сталкивается с числовым объектом-ключом `343L` (тип `Long`), которого не было в мапе `user_details`. Аллокация ячейки под новый ID снова активирует `synchronized`.
   4. **Первичный вход старого пользователя после перезапуска инстанса (`POST /api/users/login`):** Если зарегистрированный ранее игрок выполняет вход на «холодный» после перезагрузки инстанса Caffeine-кэш, его строкового ключа в RAM текущей сессии еще нет, что приводит к штатному выделению бакета памяти под замком монитора.
   5. **Истечение времени жизни кэша (TTL Eviction) под высокой нагрузкой:** Спустя 10 минут (`expire-after-write`) кэш списков автоматически сбрасывается. При первой же параллельной лавине gRPC-запросов активируется механизм `sync = true`. Caffeine атомарно блокирует дублирующие потоки, пропуская в БД только один первый поток. Запись обновленного значения в пустую ячейку памяти мапы кэша кратковременно активирует внутренний монитор синхронизации бакета.

   **Архитектурный вывод:** Все 5 сценариев происходят **исключительно внутри оперативной памяти (In-Memory RAM)** за микросекундные доли времени для выделения, удаления или перезаписи ссылок. Данный пиннинг **не является блокирующим фактором для High-Load архитектуры**, так как несущий поток ОС не засыпает, не простаивает и не ожидает дискового или сетевого ввода-вывода (I/O) до СУБД. Все повторные обращения к прогретым ключам полностью перехватываются Caffeine-кэшем (`sync = true`) и обрабатываются виртуальными потоками со стопроцентной эффективностью. Полное исчезновение данного варнинга ожидается на уровне платформы в LTS-релизах Java 25+, где OpenJDK завершит миграцию внутренних мониторов ConcurrentHashMap на неблокирующие примитивы (JEP 491 / ReentrantLock).



## 🚀 Запуск проекта

### Требования
* Установленный JDK 21
* Запущенная СУБД PostgreSQL с базой данных `game`
* Активный `Eureka-microservice` на порту 1111

### Порядок запуска
1. Перейти в папку `USERS-microservice`.
2. Запустить проект стандартной командой Maven сборщика. При первом старте плагин `protobuf-maven-plugin` автоматически сгенерирует Java-классы на основе `.proto` файла, а плагин `maven-antrun-plugin` перепишет сгенерированные аннотации на современный стандарт `jakarta.annotation`.
3. **Важно для диагностики Loom:** При запуске JAR-файла рекомендуется передавать JVM-аргумент `-Djdk.tracePinnedThreads=short`. Это позволит контролировать отсутствие Thread Pinning (блокировки несущих ОС-потоков) в критических секциях Hibernate, Spring Security и драйвера СУБД при работе с виртуальными потоками под высокой нагрузкой.
