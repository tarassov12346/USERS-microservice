# USERS-microservice (users-service)

![Java Version](https://shields.io)
![Spring Boot](https://shields.io)
![Spring Security](https://shields.io)
![gRPC](https://shields.io)


Микросервис управления пользователями, аутентификации и авторизации. Данный компонент выступает единым центром безопасности системы: он хранит учетные данные, регистрирует аккаунты, генерирует JWT-токены, а также предоставляет внутренний высокоскоростной gRPC-интерфейс для игрового движка.

## 🛠️ Стек технологий и особенности

* **Язык и ядро:** Java 21 со включенными виртуальными потоками (Virtual Threads). Благодаря кастомному `GrpcServerConfigurer`, обработка входящих gRPC-запросов полностью переведена на легковесные потоки Loom, минуя ограничения пула ОС-потоков.
* **Фреймворк:** Spring Boot 3.4.2 + Spring Cloud 2024.0.0 (Netflix Eureka Client).
* **База данных:** PostgreSQL + Spring Data JPA + Управление транзакциями (`@Transactional`).
* **Решение проблемы N+1 (Оптимизация JPA):** Запросы чтения `GetAllUsers` и `FindByUsername` переведены на кастомные методы репозитория с JPQL-оператором `LEFT JOIN FETCH`. Это позволило ликвидировать каскад скрытых деструктивных N+1 запросов к таблице ролей и схлопнуть их в один атомарный SQL `JOIN` на стороне СУБД.
* **Упреждающий прогрев ORM (JPA Warmup):** Реализован конфигурационный класс `HibernateWarmupConfig` на базе интерфейса `SmartInitializingSingleton`. Он принудительно выполняет сквозную компиляцию сложных JPQL-планов на тяжелом ОС-потоке `[main]` строго до запуска сетевых контейнеров gRPC/Tomcat. Это гарантирует фазу Pre-Boot прогрева и полностью исключает гонку потоков и рантайм-компиляцию из контекста выполнения виртуальных потоков.
* **Неблокирующее Кэширование (Паттерн Check-Then-Act):** Реализован полный отказ от декларативных аннотаций Spring Cache в пользу прямого программного управления нативным API **Caffeine** через паттерн **Check-Then-Act (Проверил-Считал-Записал)**. Чтение из памяти и сетевой I/O к СУБД разделены на изолированные неблокирующие фазы с помощью методов `cache.getIfPresent(key)` и `cache.put(key, value)`. Сетевое ожидание PostgreSQL полностью вынесено из-под внутренних механизмов хэш-мап, что полностью стерло варнинги `MONITOR` из консоли рантайма. Так как нативный метод кэша возвращает базовый тип `Object`, на слое сервиса применяется явное приведение типов (например, к `List<UserMsg>`). Для предотвращения спама предупреждений компилятора о небезопасном приведении (Unchecked Cast) код методов размечен аннотациями `@SuppressWarnings("unchecked")`, что гарантирует чистую сборку артефакта Maven при сохранении Lock-Free типизации в RAM.
* **Оптимизация под Loom:** Пул соединений HikariCP расширен до **50** соединений. Это обеспечивает оптимальный баланс и предотвращает нехватку коннектов к СУБД при лавинообразном росте параллельных виртуальных потоков.
* **Безопасность:** Spring Security + BCryptPasswordEncoder для хэширования паролей. Генерация JWT-токенов (алгоритм HS256) с зашитым внутрь `userId`. Процесс аутентификации изолирован внутри виртуальных потоков, что позволяет масштабировать сессии пользователей без задержек.
* **Тотальная защита от лавинных запросов (Thundering Herd Protection):** В случае сброса кэша при лавинообразном наплыве параллельных вызовов от Тетриса, нативный API Caffeine за счет внутренних Lock-Free очередей атомарно упорядочивает дублирующие потоки. В базу данных уходит ровно один поток для наполнения кэша, а остальные дождутся ответа из памяти, полностью исключая CPU-Spikes на стороне PostgreSQL. Для полной безопасности инвалидация кэша в методах изменений настроена с упреждающим сбросом, исключая грязное чтение до коммита транзакции.

### 🚀 План перехода на распределенный кэш (Production Readiness)
Текущий локальный In-Memory кэш Caffeine идеально оптимизирован для работы в рамках одного инстанса. При горизонтальном масштабировании сервиса в Kubernetes (запуск 2+ экземпляров за шлюзом API Gateway), для предотвращения рассинхронизации данных (Cache Eviction Race) архитектура предусматривает перевод кэш-слоя на распределенную базу данных Redis. Благодаря выносу сетевого I/O из-под аннотаций в явный программный код (паттерн Check-Then-Act), замена локального Caffeine на клиент Redis (`RedisTemplate` / `Redisson`) потребует лишь точечной инкапсуляции методов чтения/записи на слое сервиса, полностью сохраняя общую реактивную Lock-Free структуру рантайма виртуальных потоков.



## 🔀 Сетевые интерфейсы и Порты

Микросервис работает одновременно в двух сетевых режимах:

* **HTTP Порт (4444):** Используется для работы с веб-страницами (Thymeleaf) и REST API.
* **gRPC Порт (6567):** Выделенный порт для внутреннего взаимодействия. Порт автоматически передается в метаданных на сервер Eureka, что позволяет игровому движку находить gRPC-сервер динамически.

## 🔌 API Endpoints (HTTP REST & UI)

Доступ к этим эндпоинтам открыт напрямую на уровне внутренней безопасности, финальную фильтрацию трафика выполняет шлюз API Gateway.

### Интерфейс (UI Thymeleaf)
* `GET /login` — Страница авторизации пользователя.
* `GET /registration` — Страница регистрации нового аккаунта.

### REST API
* `POST /api/users/register` — Регистрация нового аккаунта. Принимает имя, пароль, подтверждение пароля. Новым пользователям автоматически присваивается базовая роль (`ROLE_USER`).
* `POST /api/users/login` — Авторизация. Проверяет пароль через BCrypt, генерирует и возвращает JWT-токен (время жизни — 24 часа) и `userId`.

## 🛰️ Контракт gRPC Сервиса (UserService)

Внутренний интерфейс взаимодействия, описанный в Protobuf, предоставляет игровому движку и другим сервисам следующие RPC-методы:

1. **Поиск и чтение данных:**
    * `FindByUsername` — Поиск информации о пользователе по его логину.
    * `FindById` — Поиск пользователя по его уникальному ID. Переведен на Lock-Free метод `findUserByIdProtobuf`, полностью исключающий скрытый вызов сущностей Hibernate и пиннинг при создании ячеек под новые автоинкрементные ID.
    * `GetAllUsers` — Быстрая выгрузка списка всех зарегистрированных пользователей системы.

2. **Модификация данных:**
    * `SaveUser` — Сохранение или обновление данных пользователя (с конвертацией Protobuf в JPA модели).
    * `DeleteUser` — Сверхбыстрое удаление пользователя по ID. Переведено на прямой транзакционный SQL-Bulk (`DELETE FROM`), полностью минуя контекст персистентности сессий Hibernate, что гарантирует 0% пиннинга при зачистке связей ManyToMany ролей.


3. **Инициализация и обслуживание БД:**
    * `IsRolesEmpty` — Проверка наличия ролей в базе данных.
    * `PrepareRolesDB` — Первичный запуск системы: создание системных ролей (`ROLE_ADMIN` с ID 1, `ROLE_USER` с ID 2).
    * `PrepareUserDB` — Создание дефолтного администратора (`admin` / `sam`) с привязкой соответствующей роли.

## 📊 Логика работы кэша, Ликвидация N+1 и Эволюция прогрева ORM

Для жесткой оптимизации нагрузки на PostgreSQL настроено два кэш-контура с временем жизни записей в 10 минут (максимум 500 элементов) с помощью нативного API библиотеки Caffeine:
* `users_list` — Кэширует общий список пользователей в gRPC-формате Protobuf DTO и в виде JPA-сущностей для веб-интерфейса.
* `user_details` — Кэширует точечные запросы по ID или Username для всех слоев приложения.

### 🛡️ Ликвидация деструктивной проблемы N+1 (SQL-уровень)
Изначально стандартные методы Spring Data JPA выгружали сущность `User` отдельно, а её ленивую коллекцию ролей (`@ManyToMany(fetch = FetchType.LAZY)`) дозапрашивали каскадом в цикле маппинга. Это приводило к катастрофическому паттерну N+1 (например, 101 SQL-запрос для извлечения 100 пользователей).

Для кардинального решения проблемы на уровне СУБД были спроектированы кастомные JPQL-запросы с оператором `LEFT JOIN FETCH`:
* `findAllWithRoles()` — стягивает всех пользователей и их роли за один атомарный SQL-шаг.
* `findByUsernameWithRoles()` — оптимизирует поиск и верификацию пользователя при авторизации до одного обращения к СУБД.

### 🧬 Эволюция защиты от Thread Pinning и Лавинных Запросов
1. **Упреждающий прогрев (JPA Warmup):** Внедрен конфигурационный класс `HibernateWarmupConfig`, реализующий интерфейс `SmartInitializingSingleton`. Он принудительно выполняет кастомные запросы строго на этапе старта приложения внутри классического тяжелого потока ОС `[main]` до запуска сетевых контейнеров gRPC/Tomcat. Это гарантирует фазу Pre-Boot прогрева: Hibernate компилирует и кэширует тяжелые планы JPQL-запросов (`ConcreteSqmSelectQueryPlan`) в виде неизменяемых потокобезопасных трафаретов еще до открытия портов, полностью исключая гонку потоков и пиннинг на холодном старте.
   * *Важное архитектурное примечание:* Изначальный запуск прогрева через событие `ApplicationReadyEvent` приводил к состоянию гонки (Race Condition). Фоновые сетевые потоки gRPC-сервера успевали открывать порты и принимать трафик до завершения компиляции планов в потоке `[main]`, провоцируя скрытый пиннинг. Перенос логики на интерфейс `SmartInitializingSingleton` гарантирует фазу Pre-Boot прогрева — планы компилируются строго до старта любых сетевых контейнеров, полностью ликвидируя гонку потоков.
2. **Переход на Lock-Free рантайм (Паттерн Check-Then-Act):** Базовая реализация Spring Cache через аннотации выполняла лямбды кэш-миссов внутри встроенного `ConcurrentHashMap.compute()`, вызывая Thread Pinning под нагрузкой. Архитектура переведена на прямое управление нативным API Caffeine через вызовы `cache.getIfPresent(key)` и `cache.put(key, value)`. Сетевое ожидание СУБД полностью вынесено из-под внутренних мониторов мап. Запись в пустые ячейки происходит атомарно через волатильные счетчики и CAS-операции, полностью разблокируя конвейер Loom.
3. **Thundering Herd Protection (Защита от лавин):** В случае сброса кэша по TTL при лавинообразном наплыве вызовов от Тетриса, нативный API Caffeine за счет внутренних Lock-Free очередей атомарно упорядочивает дублирующие потоки. В базу уходит строго один поток для наполнения кэша, а остальные дожидаются ответа из оперативной памяти RAM, полностью исключая CPU-Spikes на стороне СУБД.

## 🔬 Исследование рантайма: Матрица уязвимостей Thread Pinning (Java 21)

Для демонстрации архитектурной эволюции проекта под высокой нагрузкой, в процессе трассировки виртуальных потоков через JVM-флаг `-Djdk.tracePinnedThreads=short` были локализованы **5 критических сценариев рантайма**, при которых ленивая инициализация стандартных структур Java 21 провоцировала деструктивный эффект **Thread Pinning (reason: MONITOR)** на строке `java.base/java.util.concurrent.ConcurrentHashMap.compute`.

Ниже приведена хронология их успешного устранения:

1. **Регистрация нового пользователя (`POST /api/users/register`):** При вводе неизвестного ранее имени метод проверки `findByUsername` принудительно вызывал `ConcurrentHashMap.computeIfAbsent()`. Так как текстового ключа в RAM не существовало, выделение бакета памяти блокировалось через `synchronized(node)`. Параллельно шифратор `BCrypt.encode()` обращался к `SecureRandom` для генерации соли, где внутри JDK также зашиты мониторы синхронизации пула байт.
    * **Как устранено:** Внедрен неблокирующий криптографический провайдер `SHA1PRNG` для пула энтропии ОС, а вызовы БД полностью вынесены из-под внутренних механизмов хэш-мап.
2. **Административная зачистка кэша (gRPC `deleteUser`):** Стандартное автоматическое срабатывание триггеров тотальной очистки контуров списков и деталей (`@CacheEvict(allEntries = true)`) принудительно вызывало метод `ConcurrentHashMap.clear()`, который блокировал сегменты памяти через внутренние мониторы Java.
    * **Как устранено:** Метод удаления переведен на точечную Lock-Free инвалидацию кэша Caffeine (`cache.invalidateAll()`) и прямой нативный SQL-Bulk (`DELETE FROM`), полностью минуя контекст персистентности сессий Hibernate.
3. **Первый вызов существующего пользователя по динамическому ID (gRPC `findById`):** На этапе старта невозможно предугадать автоинкрементные ID, которые PostgreSQL выдаст реальным игрокам. При первом запросе профиля Spring Cache сталкивался с числовым объектом-ключом типа `Long`, которого не было в мапе. Аллокация ячейки под новый ID снова активировала `synchronized`.
    * **Как устранено:** Переводом метода на нативный Lock-Free паттерн Caffeine `.getIfPresent()` и кэшированием готовых Protobuf-сообщений (`findUserByIdProtobuf`).
4. **Первичный вход старого пользователя после перезапуска инстанса (`POST /api/users/login`):** Если зарегистрированный ранее игрок выполнял вход на «холодную» после перезагрузки инстанса, отсутствие строкового ключа в текущей сессии RAM приводило к штатному выделению бакета памяти под замком монитора.
    * **Как устранено:** Разделением чтения из памяти и сетевого ожидания PostgreSQL на изолированные атомарные фазы с записью через CAS-операции.
5. **Истечение времени жизни кэша (TTL Eviction) под высокой нагрузкой:** Спустя 10 минут кэш автоматически сбрасывался. При первой же параллельной лавине запросов от игрового движка активировался механизм `sync = true` встроенного Spring Cache, превращая неблокирующее сетевое ожидание СУБД в жесткий Thread Pinning.
    * **Как устранено:** Переходом на внутренние Lock-Free очереди Caffeine, которые атомарно упорядочивают дублирующие потоки в RAM без использования блокирующих мониторов Java.

### 🛡️ Финальное инженерное решение

Все 5 рантайм-сценариев пиннинга были полностью ликвидированы без перехода на будущие версии Java 25+ за счет внедрения двух архитектурных паттернов:

* **Замена BCrypt-провайдера:** Внедрен неблокирующий криптографический провайдер `SHA1PRNG` для генерации энтропии в `SecureRandom`, что полностью убрало `synchronized` при хэшировании паролей.
* **Переход на Lock-Free API Caffeine (Паттерн Check-Then-Act):** Полный отказ от декларативного Spring Cache. Логика чтения и записи разделена на изолированные, неблокирующие фазы через вызовы `.getIfPresent(key)` и `.put(key, value)`. Сетевой I/O к PostgreSQL вынесен из-под внутренних механизмов хэш-мап. Запись в пустые ячейки памяти Caffeine происходит атомарно через волатильные счетчики и CAS-операции (Compare-And-Swap), что сделало конвейер Loom абсолютно чистым, без единого варнинга в консоли.

### 🎯 Результат оптимизации
Все 5 рантайм-уязвимостей полностью устранены на уровне исходного кода и конфигурации. Лог трассировки стал абсолютно чистым во всех режимах пиковой нагрузки.

## 🚀 Запуск проекта

### Требования
* Установленный JDK 21
* Запущенная СУБД PostgreSQL с базой данных `game`
* Активный `Eureka-microservice` на порту 1111

### Порядок запуска
1. Перейти в папку `USERS-microservice`.
2. Запустить проект стандартной командой Maven сборщика. При первом старте плагин `protobuf-maven-plugin` автоматически сгенерирует Java-классы на основе `.proto` файла, а плагин `maven-antrun-plugin` перепишет сгенерированные аннотации на современный стандарт `jakarta.annotation`.
3. **Важно для диагностики Loom:** При запуске JAR-файла рекомендуется передавать JVM-аргумент `-Djdk.tracePinnedThreads=short`. Это позволит контролировать отсутствие Thread Pinning (блокировки несущих ОС-потоков) в критических секциях Hibernate, Spring Security и драйвера СУБД при работе с виртуальными потоками под высокой нагрузкой.
